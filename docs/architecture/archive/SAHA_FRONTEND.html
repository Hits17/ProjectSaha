1 · What the frontend is

The Saha marketplace web app (apps/frontend) is a Next.js 15 application on the App Router, styled with an in-house "institutional-trust" design system on Tailwind v4 (design tokens in globals.css @theme + an accessible, zero-dependency component library in components/ui/). Server data flows through TanStack Query (hooks in lib/hooks.ts) over one typed fetch client; auth/session state is in Zustand. It is the member-facing surface for the entire IP funnel — register, verify, list, discover, propose, transact, settle, review, socialise in communities, and receive real-time notifications. (Administration lives in a separate app, apps/admin, on port 3002.)

app/ — routes & layouts (App Router) store/ — Zustand auth state lib/api.ts — typed API client components/ — shared UI Tailwind — utility styling

Client-rendered, hardened token-auth

Dashboard pages are "use client" components that read the short-lived access token from the Zustand store. The long-lived refresh token is an httpOnly, SameSite cookie (never in localStorage, so XSS can't steal it); the API client refreshes transparently on 401 via that cookie.

One client, fully typed

Every backend call goes through api.<domain>.<method>() in lib/api.ts, which mirrors the backend's TypeScript types and centralises errors + token refresh. Pages never call fetch directly.

Route groups = trust zones

The folder structure encodes access: (auth) for logged-out, (dashboard) for members (guarded by a layout redirect), and a public /listings/[id] server route for SEO.
How to read this document. Component-organised, like its backend sibling. The anatomy and page pattern sections teach the one shape every page repeats; the catalogue then enumerates every route. Diagrams render live via Mermaid (CDN — needs internet once).

5 · Layouts & navigation

Three layouts nest: the root layout (app/layout.tsx) sets up <html>/fonts and wraps everything; the auth layout centres the login/register cards; the dashboard layout (app/(dashboard)/layout.tsx) is the workhorse.

The dashboard layout does three jobs

  1. Route guard. On mount, if (!isAuthenticated()) router.push("/login"); it renders nothing until a user is present — no flash of protected content.
  2. Role-aware nav. Admins get ADMIN_NAV; everyone else gets the unified MARKETPLACE_NAV — Dashboard · Listings · Discover · Materials · Community · Demand · Proposals · Transactions · Security (each with a lucide-style inline icon). A notification bell (SSE-driven, unread badge) sits in the header. (Open-roles model: creators and manufacturers share one nav.)
  3. Active-link highlighting. usePathname() drives an isActive(href, exact) check; the current section gets the filled slate-900 pill. A separate compact bar renders the same links on mobile.
Adding a feature to the nav is a one-line change in MARKETPLACE_NAV — that is exactly how the Community tab was added alongside the backend slice.

6 · Auth store (Zustand)

store/auth.ts is a Zustand store wrapped in the persist middleware. It is the single source of identity for the whole client.

interface AuthState {
  user, accessToken, refreshToken,
  setAuth(user, access, refresh),   // login success
  setUser(user),                    // after /users/me refresh
  setTokens(access, refresh),       // after token rotation
  clearAuth(),                      // logout
  isAuthenticated(): boolean,       // !!accessToken
}
persist(..., { name: "saha-auth",
  // Security: refresh token is NOT persisted — it lives only in an httpOnly cookie.
  partialize: s => ({ accessToken, user }) })
  • Persistence. Only the short-lived access token + user are written to localStorage["saha-auth"]; the refresh token stays in an httpOnly cookie the browser sends to /api/v1/auth/*. A page refresh keeps you logged in, and when the access token expires the API client silently refreshes via the cookie.
  • Read anywhere. Pages call const { accessToken, user } = useAuthStore(); the layout guard calls isAuthenticated().
  • Updated by the API client too. When the token is silently rotated on a 401, tryRefresh() writes the new tokens straight back into this store (see §8).

7 · The API client — lib/api.ts

This one file is the entire contract with the backend: the TypeScript mirror of every response shape, plus a namespaced method for every endpoint. Pages never touch fetch directly — they import api.

The core: request<T> + ApiError

async function request<T>(path, { token, ...opts }): Promise<T> {
  headers = { "Content-Type": "application/json",
              Authorization: token && `Bearer ${token}` }
  res = await fetch(BASE_URL + path, { ...opts, headers })
  if (res.status === 204) return undefined          // no-content
  if (res.status === 401 && token) {                // ← auto-refresh
     newToken = await tryRefresh()
     if (newToken) retry once with the new Bearer
  }
  data = await res.json()
  if (!res.ok) throw new ApiError(res.status, data.detail)
  return data as T
}

Everything funnels through here, so error handling is uniform: a failed call throws an ApiError carrying the HTTP status and the backend's detail string, which pages catch and surface inline.

8 · The 401 auto-refresh handshake

Access tokens expire; the client hides that from the user. When any authenticated call returns 401, request<T> calls tryRefresh() once, and on success replays the original request with the new token — the page never sees the failure.

Transparent token rotation inside the API client
sequenceDiagram
  autonumber
  participant P as Page
  participant API as lib/api.ts
  participant S as Zustand store
  participant BE as Backend
  P->>API: api.x.method(accessToken)
  API->>BE: fetch + Bearer (expired)
  BE-->>API: 401
  API->>S: read refreshToken
  API->>BE: POST /auth/refresh
  alt refresh ok
    BE-->>API: new access + refresh
    API->>S: setTokens(new)
    API->>BE: retry original with new Bearer
    BE-->>P: data
  else refresh fails
    API-->>P: throw ApiError(401) → redirect to /login
  end

Because tryRefresh() dynamically imports the store and writes the rotated tokens back, the persisted session stays valid across the whole tab without any page-level retry logic.

9 · Anatomy of a page

Every dashboard page is the same shape. Recognise it once and all of them read the same way:

"use client";                                  // client component
export default function XPage() {
  const { accessToken, user } = useAuthStore(); // 1. identity from store
  const [data, setData] = useState<T | null>(null);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState("");

  const load = useCallback(async () => {        // 2. fetch via api client
    if (!accessToken) return;
    setLoading(true);
    try { setData(await api.x.method(accessToken)); }
    catch (e) { setError(e instanceof ApiError ? e.message : "…"); }
    finally { setLoading(false); }
  }, [accessToken]);

  useEffect(() => { load(); }, [load]);          // 3. on mount / token change
  // 4. render: loading / error / empty / data branches
}

The conventions are consistent across the codebase: accessToken + user from the store; data/loading/error triad; useCallback loaders keyed on the token; ApiError messages surfaced inline in a red panel; explicit empty-states. A KYC gate (user?.kyc_status === "verified") hides write actions until the member is verified.

12 · Community & group chat (the social UI)

The social feature adds two client pages that follow the page pattern, with one addition unique to chat: polling.

/dashboard/community

Two tabs — Discover (browse public communities with a topic filter) and My Communities — plus an inline create form (name, description, 1-of-10 topic, public/private). Each card shows member_count and either a Join button or an Open-chat link based on is_member. Creating or joining routes straight into the community.

/dashboard/community/[id]

The chat room: a scrolling message list (own messages right-aligned in slate, others left in grey with sender name), a member sidebar with role badges, and join/leave controls. A composer posts via communities.postMessage; an auto-scroll ref keeps the newest message in view.

How the chat stays live

There is no WebSocket; the room polls. While the viewer is a member, a useEffect kicks off loadChat() immediately and then on a setInterval(…, 5000), cleared on unmount. Messages and members load together via Promise.all; a 403 on the chat endpoint (non-member) is swallowed and turned into a "join to read" prompt instead of an error. Posting optimistically appends the returned message so the sender sees it instantly between polls.

Design note. 5-second polling is the MVP choice — simple and robust on the edge host. A realtime upgrade (WebSocket/SSE) would slot in behind the same api.communities surface without touching the page's render logic.

15 · Conventions & gotchas

RuleWhy
"use client" on interactive pagesDashboard pages use hooks (useState/useEffect/store) — they must be client components. Public listing pages stay server components for SEO.
Next.js 15 params is a PromiseServer pages must const { id } = await params; client pages read it with useParams<{id:string}>().
Never call fetch in a pageGo through api.* so auth headers, 401 refresh, and error shaping stay centralised.
Catch ApiError, show .messageThe backend's detail string is the user-facing message; surface it inline rather than a generic error.
Gate writes on kyc_status === "verified"Mirrors the backend's require_verified_user; hides actions the API would 403 anyway.
Clear intervals on unmountThe community chat poller returns its clearInterval from useEffect to avoid leaks/duplicate polls.
NEXT_PUBLIC_API_URLThe API base URL is an env var (defaults to http://localhost:8000); set it per environment.
