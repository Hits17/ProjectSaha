1 · System Overview

Saha is a vertically-integrated Transaction Operating System for Intellectual Property. It takes an IP holder (a creator) and a manufacturer from discovery all the way through to a legally-signed, escrow-settled licensing deal — with AI assistance, encrypted document exchange, KYC identity assurance, and platform-mediated payments at every step. This document maps every container, every API call, every integration, and every byte of plumbing from the perspective of a solutions architect.

Open-roles model (2026-06-10). creator/manufacturer is a signup label, not a capability boundary: every verified member can list IP and discover/bid on IP. Marketplace authorization is ownership-based ("not your listing", "cannot propose on your own listing"); only admin/legal remain privileged. The same release added the raw-materials secondary marketplace (/api/v1/materials): members list materials they can supply regionally, so IP buyers can procure production inputs locally and keep backup suppliers.
Social layer (2026-06-18). A communities feature (/api/v1/communities) adds the social dimension: members create topic communities (themed to IP R&D domains — biotech, clean energy, materials science…) and group-chat inside them to share ideas and advance research & development. Reading public communities needs only authentication; creating, joining and posting require verified KYC; reading a community's chat requires membership. See §20.

The Spine

A 9-stage funnel: Identity → List → Discover → Negotiate → Legal → Settle → Review → Sense Demand → Govern. Each stage is an isolated domain module sharing one async runtime.

Trust by Design

AES-256-GCM at rest, JWT + refresh-family rotation, AI-mediated PII firewall, mandatory KYC gating, platform-held escrow. Parties never exchange contact details or funds directly.

Edge-Native

Runs on a single NVIDIA Jetson Orin Nano (ARM64). Native PostgreSQL + Dockerised stateful services. Heavy AI is offloaded to cloud inference (NVIDIA NIM / Anthropic).

6 · Request Lifecycle & Middleware Pipeline

Every inbound HTTP request passes through the same pipeline before it reaches a route handler, and a deterministic teardown after. Understanding this pipeline explains auth, CORS, rate-limiting, the DB-session boundary, and audit logging in one picture. An outer middleware assigns/propagates X-Request-ID, emits one structured access-log line per request (structlog), converts unhandled exceptions into a generic 500 with the request id, and stamps security headers (nosniff, X-Frame-Options: DENY, referrer-policy, HSTS in production) on every response.

DB-session boundary

The get_db() dependency yields one AsyncSession per request, rolls back on any exception, and always closes in finally. expire_on_commit=False keeps objects usable after commit — hence the populate_existing=True pattern when re-reading mutated rows with fresh relationships.

Audit as background work

Mutating endpoints append to audit_logs via BackgroundTasks after the response is computed, so logging never blocks or fails the user's request. Actions: transaction.contract_signed, settlement.disbursed, review.created, etc.

7 · Authentication & Refresh-Token Rotation

Saha uses short-lived access JWTs (HS256) paired with long-lived, single-use refresh tokens organised into families. Only a SHA-256 hash of each refresh token is ever stored. Reuse of an already-rotated token is treated as theft and nukes the entire family.

7.2 Rotation & Theft Detection

When the access token expires, lib/api.ts transparently calls /auth/refresh on a 401 and retries the original request once. The server rotates the refresh token within the same family_id and marks the old one used_at. If a token that already has used_at is presented again, the whole family is deleted.

Sequence — silent refresh + reuse-detection security tripwire
sequenceDiagram
  autonumber
  participant FE as lib/api.ts
  participant API as FastAPI /auth
  participant SVC as auth service
  participant DB as refresh_tokens

  FE->>API: GET /protected (expired access)
  API-->>FE: 401
  FE->>API: POST /auth/refresh {raw_refresh}
  API->>SVC: refresh_access_token()
  SVC->>DB: SELECT WHERE token_hash = sha256(raw) AND not expired
  alt token not found
    SVC-->>FE: 401 invalid/expired
  else token.used_at IS NOT NULL  (REUSE!)
    SVC->>DB: DELETE all WHERE family_id = token.family_id
    SVC-->>FE: 401 "Token reuse detected — log in again"
  else valid & unused
    SVC->>DB: UPDATE used_at = now()
    SVC->>SVC: new access + new refresh (same family_id)
    SVC->>DB: INSERT rotated refresh_token
    SVC-->>FE: {access_token, refresh_token}
    FE->>API: retry /protected (new access)
    API-->>FE: 200
  end
Why hashes + families? A DB compromise yields only SHA-256 hashes — useless for replay. Rotation makes every refresh single-use; the family mechanism converts a stolen-token replay into an automatic, self-healing logout of the attacker and the victim, prompting re-authentication.

8 · Authorization — RBAC & KYC Gating

Three FastAPI dependencies form a ladder of trust. Public endpoints use the optional variant; transactional endpoints demand verified identity; the admin console demands the admin role.

get_optional_user

auto_error=False Returns User | None. Used by public listing reads so anonymous browsing works but personalised data appears when logged in.

require_verified_user

403 unless kyc_status == VERIFIED. Guards listing creation, materials, proposals, transactions, settlement, reviews, and community writes (create/join/post) — anything that creates legal, financial, or social obligation.

require_admin

403 unless role == ADMIN. Guards the entire /api/v1/admin/* surface.

9.2 Embeddings path (separate from chat)

Semantic vectors are produced by services/embeddings.py calling NVIDIA nv-embedqa-e5-v5 (1024 dims) directly over HTTPS — not through the chat client. 10 · Data Model — Entity Relationship Diagram

20 tables in one PostgreSQL database. The IP funnel reads left-to-right: a user owns ip_listings; each listing has bom_items + encrypted ip_vault_assets; a proposal joins buyer↔listing and carries proposal_versions + encrypted messages; an accepted proposal spawns a transaction, which yields a disbursement and post-close reviews. raw_material_listings is the secondary marketplace (seller→materials). The social layer adds communities with their community_memberships join and community_messages (plaintext group chat). demand_signals and audit_logs are cross-cutting ledgers.

12 · Domain Flow — Vault Encryption at Rest

Confidential files (the actual IP) never hit disk in plaintext. On upload they are sealed with AES-256-GCM; the ciphertext layout is nonce(12 bytes) ‖ GCM ciphertext+tag, stored as one MinIO object. The 256-bit key is derived as SHA-256(VAULT_ENCRYPTION_KEY).

Sequence — encrypt-on-upload, presign / decrypt-on-authorized-read
sequenceDiagram
  autonumber
  participant FE as Next.js
  participant API as /listings/{id}/files
  participant V as vault svc
  participant S3 as MinIO
  participant PG as PostgreSQL

  FE->>API: POST file (multipart)
  API->>V: store_encrypted_file(listing_id, name, bytes)
  V->>V: key = SHA256(VAULT_ENCRYPTION_KEY)
  V->>V: nonce = os.urandom(12)
  V->>V: blob = nonce ‖ AESGCM(key).encrypt(nonce, data)
  V->>S3: put_object(vault/{lid}/{aid}/name.enc, blob)
  V->>PG: INSERT ip_vault_assets(storage_key, key_id=v1, size)
  API-->>FE: 201 asset metadata

  Note over FE,S3: Authorized read (post escrow-funded — see §16)
  FE->>API: GET …/vault-access (list) → download_path per asset
  FE->>API: GET …/vault-access/{asset}/download (Bearer JWT)

Two crypto surfaces, one routine. The same _encrypt/_decrypt primitives from vault.py also seal proposal messages (stored as BYTEA in Postgres). Files live in MinIO; messages live in Postgres — but both are GCM-sealed with the same derived key.

20 · Domain Flow — Social Communities & Group Chat

The social layer lets members gather around an IP R&D topic and talk. It deliberately inverts the secrecy model of proposal messaging: where a proposals.messages thread is private, AES-256-GCM-encrypted and PII-firewalled (parties must not swap contact details), a community_messages thread is the opposite — open group discussion stored as plaintext, where membership is the only access boundary. Three tables back it: communities (the group, with a unique generated slug + public/private visibility), community_memberships (a UNIQUE(community_id, user_id) join carrying an owner/moderator/member role), and community_messages.

Authorization split

Reads of public communities need only get_current_user; writes (create · join · leave · post · edit) need require_verified_user (KYC); reading a community's chat additionally requires membership (403 otherwise). Private communities are invisible to non-members and cannot be self-joined.

Owner lifecycle

Creating a community runs in one transaction: flush() assigns the id, then the creator is inserted as an OWNER membership. Owners cannot leave their own community (400). Slugs are generated from the name; collisions get a -{6 hex} suffix.

Read model

Each CommunityResponse is enriched per request with member_count, the caller's is_member, and their my_role. Chat fetches return newest-N then reverse to oldest-first for natural rendering; messages carry the sender's display name (joined from users).
Sequence — discover → join → post → read (membership gate)

Why plaintext here is correct. The proposal PII firewall exists to stop two negotiating parties from taking a deal off-platform. A community is the explicit opposite intent — open collaboration to encourage R&D — so the same controls would be counter-productive. The trust boundary moves from encryption to membership: non-members can't read the chat at all, and only verified users can post.
