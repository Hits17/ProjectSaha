# Saha engineering and product review

> **Historical evidence:** Findings below describe the stated review point. Subsequent fixes and owner-confirmed rollout are recorded in [Current status](CURRENT-STATUS.md) and [Development history](DEVELOPMENT-HISTORY.md). The new social/workspace release requires additional migrations and has separate rollout evidence.

Date: 2026-10-31. Local checkout: `/home/hitarth/Downloads/saha`.

## Assessment

Saha has a coherent product thesis: help an inventor turn technical knowledge into a discoverable asset, negotiate a license, document agreement, and complete a protected handover. The strongest next milestone is one dependable end-to-end transaction, including failure recovery. Adding more social functionality or a large cloud architecture before completing that milestone would spread effort too thin.

Keep the modular monolith. FastAPI services, PostgreSQL, two Next.js applications, Redis, Qdrant and S3-compatible storage are sufficient foundations. Introduce explicit domain policies, durable side-effect processing and reproducible deployments within that architecture. A microservice rewrite is not justified by this review.

This is a review and proposed backlog, not an implementation or production certification. Application code and existing frontend edits were preserved. No real payments, provider requests, database migrations, key rotation, deployment or live-data tests were performed.

## Study coverage and boundaries

Study covered authored backend routes/services/models/schemas, AI routing/providers/prompts/session handling, auth/crypto/integrations, tests, marketplace/admin routes/components/API/auth state, SQL/Compose/CI and repository documentation. Specialized domain and frontend studies supplemented the primary review. Generated builds, dependencies, lockfile contents, secrets, local credential backups and third-party source were excluded. The frontend is a separate Git working tree with pre-existing modifications.

Historical security documents were compared against code rather than treated as current runtime evidence. They report that the old key was retired and the exclusivity index installed in August; this review did not inspect the current production database or key configuration. Findings about installed index behavior are conditional on the migration being present.

| External processes | Persona, Stripe, SMTP; internal dual signatures | Several real-provider user journeys remain incomplete |

Existing capabilities worth preserving include public/private listing response separation, ownership-based marketplace access, verified-user gates, encrypted vault and proposal messages, two-party hash-bound signatures, human moderation of held posts, an open innovation library, communities, raw-material listings, and separate social standing versus transaction reputation. These are already present, not proposed new features.

## Independent GPT-6 Astra review

The user requested a strongest-coding-model second pass. GPT-6 Astra was selected using the current official model catalog: https://developers.openai.com/api/docs/models . It independently inspected core backend, tests and CI, then reviewed the primary/domain/frontend notes. It made no application changes.

Astra agreed with the study's direction and strengthened the priority of financial correctness over search/social polish. Its top findings were MFA replacement, stale locked ORM state, payout idempotency/recovery, incomplete real payment integration, mutable overlapping contract drafts and disputed-asset exclusivity.

It reproduced stale SQLAlchemy identity-map behavior in memory. That is an ORM-semantics reproduction, not a real PostgreSQL payout/concurrency test. Proposed concurrency defects require the explicit PostgreSQL interleaving tests in the backlog before a fix is considered verified.

Corrections incorporated after the second pass:

- Do not say the exclusivity index is absent: it exists in migrations and August deployment notes report installation. The stronger current code issue is omission of disputed reservations and uncoordinated state changes.
- Scope the step-up CORS issue to cross-origin deployments.
- The frontend contract GET wrapper exists; wire the page to it rather than adding a redundant API.
- Admin dispute resolution deliberately assumes out-of-band funds movement; enforce reconciliation evidence rather than treating status changes as proof money moved.
- Old key retirement was documented as complete. The rotation issue is crash recovery of the script, not a claim of present compromise.
- A large number of passing unit/predicate tests does not establish money movement, identity provider, browser or database-concurrency correctness.

## Delivery sequence and release gates

1. **Protect identity and private content:** R01, R06–R08, R15–R19. Add real request-level tests for enrollment, session changes and every alternate content-reading surface.
2. **Make one transaction dependable:** R02–R05 and R09–R14, with isolated provider sandbox integration, simultaneous requests, worker interruption, duplicate/delayed webhooks and recoverable partial failures.
3. **Make deployment repeatable and recoverable:** R20–R22, R25, R27–R28; clean-clone build, empty/upgrade DB tests, reproducible artifacts, backup restoration and monitored dependency failure.
4. **Improve discovery and documentation quality:** R23–R24, R26, R29; trustworthy demand counts, repairable indexes and resumable typed BOM workflows.
5. **Expand the product:** start with NDA/diligence and rights/provenance, then materials RFQ and targeted alerts. Measure completion of useful exchanges before expanding portfolios or hosting complexity.

Avoid calendar promises until remaining implementation scope and provider choices are clear. Each milestone should be accepted by observable behavior and recovery evidence rather than a feature checklist.
