## The blocker that held this up

```
$ psql -U saha -d saha -f saha-dev-infra/migrations/2026-08-05-security-hardening.sql
ERROR: must be owner of table ip_vault_assets
```

Six tables the migration alters — `users`, `transactions`, `messages`,
`disbursements`, `ip_vault_assets`, `audit_logs` — are owned by `postgres`, not
`saha`. Table DDL has always needed `postgres` on this host (see the
`known_fixes` note about users-table ALTERs). Resolved by the operator running
step 1 directly.

Note for next time: `postgres` cannot read files under `~/Downloads` (no
directory traversal), so either pipe the file on stdin or stage a copy in
`/tmp`.

## Deploy sequence

Run in order. Steps 1–2 are the risky ones; both are reversible.

### 1. Migration (needs postgres)

```bash
cd ~/Downloads/saha
sudo -u postgres psql -d saha -f saha-dev-infra/migrations/2026-08-05-security-hardening.sql
```

Idempotent and transactional — safe to re-run. Expected tail: `COMMIT`.

Verify:
```bash
sudo -u postgres psql -d saha -c "\d contract_signatures"
sudo -u postgres psql -d saha -c "SELECT seq, entry_hash IS NOT NULL AS hashed FROM audit_logs ORDER BY seq DESC LIMIT 3;"
```
Existing rows carry `entry_hash IS NULL` — expected. They pre-date the chain and
the verifier treats the first hashed row as the root.

### 2. Apply the rotated MinIO credentials

They are generated and waiting in `saha-dev-infra/.env.pending-deploy`. They are
not live because rotating the container's root credentials takes effect
immediately while the running backend holds the old values in its process
environment — applying them early left the live site unable to reach object
storage, so I reverted. (Verified: `/health` showed `minio: unhealthy`, then
healthy again after the revert.)

```bash
cd ~/Downloads/saha/saha-dev-infra
cp .env.pending-deploy .env

# Mirror the same values into the backend
NEW_USER=$(grep '^MINIO_ROOT_USER=' .env | cut -d= -f2)
NEW_PASS=$(grep '^MINIO_ROOT_PASSWORD=' .env | cut -d= -f2)
sed -i "s|^MINIO_ACCESS_KEY=.*|MINIO_ACCESS_KEY=${NEW_USER}|" ../apps/backend/.env
sed -i "s|^MINIO_SECRET_KEY=.*|MINIO_SECRET_KEY=${NEW_PASS}|" ../apps/backend/.env

docker compose up -d minio
```

### 3. Build the web apps

Deliberately not done during the session: `next build` replaces `.next` in
place, and the running server would immediately start serving code that calls
endpoints (`/auth/step-up`, `/auth/stream-ticket`, `/transactions/{id}/contract`)
the old backend does not have.

`NEXT_PUBLIC_API_URL` **must** be inline on every production build or `localhost`
is baked into the bundle and login breaks (this has bitten before — see
`known_fixes`).

```bash
cd ~/Downloads/saha/apps/frontend
NEXT_PUBLIC_API_URL=https://sahasolutions.com pnpm build

cd ../admin
NEXT_PUBLIC_API_URL=http://10.0.0.228:8080 pnpm build
```

### 4. Restart, in this order

```bash
sudo systemctl restart saha-backend
sleep 8 && curl -s localhost:8000/health/live      # {"status":"alive"}

sudo systemctl restart saha-frontend
sudo systemctl restart saha-admin
```

If the backend refuses to start, that is the boot guard doing its job — read the
error, it names the exact setting. `journalctl -u saha-backend -n 50`.

### 5. Verify

```bash
# SAHA-003 — the headline fix. Must NOT contain bom_items or description.
curl -s "http://localhost:8000/api/v1/listings/public?limit=1" | python3 -m json.tool

# SAHA-004 — mock KYC must be gone
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:8000/api/v1/users/me/kyc/complete   # 401/404, never 200

# SAHA-019 — deep health is admin-only now
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8000/health          # 401/403
curl -s http://localhost:8000/health/live                                       # still open

# Public site end-to-end
curl -s -o /dev/null -w "%{http_code}\n" -H "Host: sahasolutions.com" http://localhost/
```

Then log in on the marketplace and confirm: listings load, a proposal opens, the
notification bell connects (it now mints a stream ticket first).

### 6. Vault key rotation — **do this the same day**

The v1 key is the placeholder published in this repository (SAHA-001). New
objects are written under v2 from the moment step 4 completes, but existing ones
are still wrapped under the compromised key.

```bash
cd ~/Downloads/saha/apps/backend
uv run python scripts/rotate_vault_key.py            # dry run
uv run python scripts/rotate_vault_key.py --apply
```

Then retire v1:
```bash
sed -i 's|^VAULT_ENCRYPTION_KEY=.*|VAULT_ENCRYPTION_KEY=|' .env
sed -i 's|^VAULT_V1_ROTATION_PENDING=.*|VAULT_V1_ROTATION_PENDING=false|' .env
sudo systemctl restart saha-backend
```

Until you do, every boot logs `security_action_outstanding` — deliberately, so a
pending rotation cannot quietly become permanent.

> There is exactly **1** object in the bucket right now (a demo contract) and no
> vault assets, so this rotation is nearly free today. It will not stay that way.

### 7. Audit-log least privilege — after the deploy is verified

```bash
sudo -u postgres psql -d saha -c "REVOKE UPDATE, DELETE, TRUNCATE ON audit_logs FROM saha;"
sudo -u postgres psql -d saha -c "GRANT SELECT, INSERT ON audit_logs TO saha;"
```

Held back deliberately: revoking while the previous release is still running
would break its audit writes. The append-only trigger from step 1 is already
active; this makes the refusal happen one layer earlier.

## Rollback

Nothing here is destructive, and the migration is additive only — no column is
dropped, no data rewritten.

```bash
cd ~/Downloads/saha
git stash                      # or: git checkout <previous-commit>
cp .security-backup/env.backend.<timestamp> apps/backend/.env
cd saha-dev-infra && docker compose up -d
sudo systemctl restart saha-backend saha-frontend saha-admin
```

Backups are in `.security-backup/` (gitignored — they contain secrets). The new
columns are nullable and simply go unread by the old code. The one exception:
contracts drafted *after* the deploy are encrypted, so the old code cannot read
them — there is one demo contract in the bucket today and it is untouched.

## Configuration changed on this host

| Setting | Before | After | Why |
|---|---|---|---|
| `APP_ENV` | `staging` | `production` | Matched neither guard value, so every production check was a no-op (SAHA-005) |
| `KYC_MOCK_MODE` | `true` | `false` | Anyone could self-approve to VERIFIED (SAHA-004) |
| `COOKIE_SECURE` | unset (false) | `true` | 7-day refresh cookie had no Secure flag on an HTTPS site (SAHA-010) |
| `FRONTEND_URL` | unset (localhost) | `https://sahasolutions.com` | Every verification email link was broken |
| `ALLOWED_HOSTS` | `["*"]` | explicit list | Host allow-list was disabled |
| `CORS_ORIGINS` | included two `http://` origins | HTTPS only | Plaintext origins with `allow_credentials` |
| `VAULT_ENCRYPTION_KEY_V2` | — | 48-char random | New write key (SAHA-001) |
| `REQUIRE_ADMIN_MFA` | — | `true` | Admins without a second factor are refused (SAHA-015) |
| `REQUIRE_STEP_UP_AUTH` | — | `true` | Re-auth for money movement and vault egress |
| `TRUSTED_PROXY_CIDRS` | — | loopback | Forwarding headers only honoured from the real proxy (SAHA-011) |

**After step 4, MFA becomes mandatory for admin access.** Enrol before you need
it: `POST /api/v1/auth/mfa/setup` → scan → `POST /api/v1/auth/mfa/enable`. If you
lock yourself out, `REQUIRE_ADMIN_MFA=false` in `.env` plus a restart is the
escape hatch.

## Audit chain genesis: seq 154

The chain verifies from **seq 154 onward**. Row 153 was written during a roughly
four-minute window when `write_audit_log` hashed a Python-side timestamp while
`created_at` was populated by the database's `server_default=now()` — two
different instants, so the hashed payload could never be reproduced from the
stored row. The chain was being written and was silently unverifiable, which is
the exact failure the module's own docstring warns about.

Caught by running the verifier against the live table rather than trusting that
the unit tests passing meant it worked. They did pass: every one of them operated
on hand-constructed objects, where the bug cannot appear. Two round-trip tests
against Postgres now cover it (`test_write_then_verify_roundtrip`,
`test_stored_created_at_is_the_hashed_timestamp`).

`audit_logs` is append-only, so row 153 cannot be corrected or removed — which is
the property working as intended. `verify_chain(rows, since_seq=154)` is the
correct invocation for this database. When RFC 3161 anchoring lands
([ROADMAP §3.3](ROADMAP.md)) the first timestamped root establishes genesis
formally and this note becomes redundant.

```bash
# verify the live chain
cd apps/backend && uv run python -c "
import asyncio
from sqlalchemy import select
from app.db.session import AsyncSessionLocal
from app.db.models.audit_log import AuditLog
from app.core.audit import verify_chain
async def main():
    async with AsyncSessionLocal() as db:
        rows = (await db.execute(select(AuditLog).order_by(AuditLog.seq))).scalars().all()
    print(verify_chain(rows, since_seq=154))
asyncio.run(main())"
```
